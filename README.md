# SLA Support Tracker

Реализация приёма обращений партнёров через n8n, хранения в PostgreSQL и расчёта SLA отдела заботы.

## Требования и версии

Для запуска нужны Docker с Docker Compose v2 и Python 3.12. Версии образов и пакетов зафиксированы.

| Компонент | Версия | Где задана |
|---|---|---|
| n8n | 2.45.7 | [docker-compose.yml](docker-compose.yml) |
| PostgreSQL | 17.11 | [docker-compose.yml](docker-compose.yml) |
| Python | 3.12 | [.python-version](.python-version) |
| psycopg (с binary) | 3.3.6 | [requirements.txt](requirements.txt) |
| pydantic | 2.14.2 | [requirements.txt](requirements.txt) |
| pydantic-settings | 2.16.2 | [requirements.txt](requirements.txt) |
| tzdata | 2026.6 | [requirements.txt](requirements.txt) |
| pytest | 9.2.0 | [requirements.txt](requirements.txt) |

Дополнительно:

- `make` нужен только для коротких команд из [Makefile](Makefile); без него те же команды запускаются напрямую.
- `tzdata` нужен для часового пояса `Europe/Moscow` на Windows, где нет системной базы часовых поясов.
- Порты на хосте: n8n на `127.0.0.1:5679`, PostgreSQL на `127.0.0.1:5433`. Меняются через `N8N_PORT` и `POSTGRES_PORT` в `.env`.

## Запуск
- Подготовить файл .env по примеру .env.example. Для ключа `N8N_ENCRYPTION_KEY` можно использовать команду:
```bash
openssl rand -hex 32
```
- Выполнить команду make docker-up (или docker compose up -d). При первом запуске (или если удален/пуст volume), будут выполены скрипты из sql/ папки. Создается: бд n8n, 3 таблицы бэкенда, список сотрудников и функция PostgreSQL insert_events.
- Создать окруждение, активировать и установить зависимости:
```bash
python -m venv venv
source venv/Scripts/activate
pip install -r requirements.txt
pip install -r requirements-dev.txt # для разработки
```
- настроить n8n (подробности ниже в разделе Импорт workflow и credentials):
    - http://localhost:5679 открыть страницу, создать админа.

## Импорт workflow и credentials
Нужный workflow можно найти в n8n/workflow.json. В экспорт не попадают пароли или credentials.
- создайте в n8n под админом новый workflow, импортируйте на холст файл n8n/workflow.json.
- Создайте credential для ноды PostgreSQL `insert events` открыв ее, в соответствии с данными вашего .env и docker-compose файлов:
- Порт в credential должен указывать на порт на котором работает PostgreSQL ВНУТРИ контейнера `5432`, смотреть в docker-compose.yml
- Поле `host` должно иметь строку `postgres` - название сервиса, смотреть в docker-compose.yml.
- Поле `database` из .env `POSTGRES_DB`.
- `User` и `Password` из .env `POSTGRES_USER` и `POSTGRES_PASSWORD` соответственно.
- ssl настройка disable.
- **Publish** workflow. Теперь флоу готов для обработки входящих запросов и записи данных в бд.

## Пример запроса
Запрос можно отправить из терминала (адрес вебхука лучше проверить в ноде receive events -> production url):
```bash
curl -X POST http://localhost:5679/webhook/events -H 'Content-Type: application/json' --data @fixtures/example_request.json 
```
или через postman: Метод Post, адрес смотреть в ноде receive events -> production url. Body, raw, JSON, тело из fixtures/example_request.json. Аутентификация не нужна.
- На первый вызов ожидается ответ с кодом 200 {"errors": [], "inserted": 1, "received": 1, "rejected": 0, "duplicates": 0}, на повторную отправку с отличием "inserted": 0, "duplicates": 1.

## Формат ответа и HTTP-коды
Webhook возвращает один из трёх кодов:
- `200` - запрос корректный, обработан. Код 200 приходит и тогда, когда часть событий отклонена или оказалась дублями: разобран целиком, результат по каждому событию в теле ответа.
- `422` - тело не является JSON или структура запроса неверна (нет объекта с массивом `events`, не указан `Content-Type: application/json`). В базу ничего не пишется.
- `500` - ошибка при записи в базу (например, PostgreSQL недоступен). Тело ответа в этом случае формирует сам n8n.

Тело ответа 200:
- `received` - сколько событий пришло в массиве `events`.
- `inserted` - сколько новых событий записано в базу.
- `duplicates` - сколько событий уже было в базе с теми же данными (повторная доставка).
- `rejected` - сколько событий отклонено.
- `errors` - список отклонённых событий. Всегда выполняется `inserted + duplicates + rejected = received`.

Элемент `errors`:
- `item_index` - позиция события в массиве `events`, считая с нуля.
- `event_id` - идентификатор события, `null`, если его не удалось прочитать.
- `issue_code` - код первой найденной ошибки: `invalid_<поле>` (например `invalid_occurred_at`), `invalid_event_structure` (элемент массива не объект) или `event_id_conflict` (такой `event_id` уже есть с другими данными, в базе остаётся первая версия).
- `description` - описание всех найденных проблем события.

Пример отклонённого события (в `occurred_at` нет буквы `T` и часового пояса, например `"2026-09-07 09:40"`), ответ `200`:
```json
{
  "received": 1,
  "inserted": 0,
  "duplicates": 0,
  "rejected": 1,
  "errors": [
    {
      "item_index": 0,
      "event_id": "evt-002",
      "issue_code": "invalid_occurred_at",
      "description": "Поле occurred_at: недопустимое значение, ожидается дата ISO 8601 с часовым поясом, например 2026-09-07T09:40:00+03:00"
    }
  ]
}
```

Пример неверной структуры (тело `{"data": []}`), ответ `422`:
```json
{
  "code": 422,
  "message": "Некорректная структура запроса",
  "hint": "Ожидается JSON-объект с массивом events и заголовок Content-Type: application/json"
}
```

Если тело вообще не JSON, `422` вернёт сам n8n:
```json
{"code": 422, "message": "Failed to parse request body", "hint": "Unexpected token 'o', \"not a json\" is not valid JSON"}
```

## Отчёт
Отчет собирается командой
```bash
python -m sla_support_tracker.cli --as-of 2026-09-08T12:00:00+03:00
```
или `make report AS_OF=2026-09-08T12:00:00+03:00`
- `--as-of` аргумент обязателен и только с часовымпоясом. События в бд после метки игнорируются.
- `--output-dir` необязательный аргумент, по умолчанию отчет пишется в каталог output/.

Создаются 3 файла в выбранной папке:
- `report.csv` - одна строка на `conversation_id` с колонками: `conversation_id`, `channel`, `chat_id`, `lead_id`, `first_inbound_at`, `first_response_at`, `employee_id`, `employee_name`, `actual_minutes`, `business_minutes`, `status`, `issue_reason`, `as_of`. Строки отсортированы по `conversation_id`.
- `data_issues.csv` - колонки `event_id`, `conversation_id`, `issue_code`, `description`. В файл попадают два вида записей:
    - ошибки приёма: события, отклонённые при записи (таблица `rejected_events`). `issue_code` - код первой найденной ошибки, `description` - все найденные проблемы события. Журнал выводится целиком, без фильтра по `as_of`, поэтому в нём могут быть ошибки прошлых запусков;
    - проблемы качества обращений: обращения со статусом `data_issue` (например `missing_lead_id`). Это вычисляется при построении отчёта на момент `as_of`, `event_id` у таких записей пустой.
- `summary.json` - сводные показатели: количество обращений без `data_issue`, количество по каждому статусу, `sla_compliance_percent`, `average_response_business_minutes` (оба равны `null`, если знаменатель нулевой).

Формат CSV: UTF-8 с BOM, разделитель запятая, числа с точкой, минуты с двумя знаками. Даты `first_inbound_at` и `first_response_at` в ISO 8601 по московскому времени, а `as_of` выводится в том виде, как он передан в `--as-of`.



## Тесты
Тесты запускаются из корня проекта командами:
```bash
make test
```
или 
```bash
python -m pytest
```
В базе 93 теста. Проверяется:
- расчёт рабочих минут: обычный интервал внутри дня, переход через ночь, время вне рабочего окна, другие часовые пояса, без учета выходных (`tests/sla_calculation/test_business_hours.py`).
- Правила SLA: граница между 30 минутами на первый ответ и 30 минут и 1 секунда. События ботов и системы не считаются ответом, ответ sales сотрудника не завершает ожидание ответа care сотрудника.
(`tests/sla_calculation/test_conversation_evaluation.py`)
- 17 контрольных сценариев: данные лежат в fixtures/scenarios/, ожидаемые результаты в fixtures/expected_results.json, сверка в tests/scenarios/test_control_scenarios.py (`tests/scenarios/test_control_scenarios.py`)
- запись в БД и повторная попытка записи: тот же payload не создаёт новых строк, конфликт event_id сохраняет первую версию строки (`tests/integration/`) 
- формат отчётов: колонки CSV, кодировка, сводка (`tests/reporting/`, `tests/test_cli.py`).

Интеграционные тесты работают с запущенным PostgreSQL (`make docker-up`) и выполняются внутри транзакции, которая откатывается и данные в базе не остаются. Если базы нет, они пропускаются, остальные тесты проходят без неё.

Отдельно от `pytest` есть сквозная проверка приёма через webhook: `make send-fixtures` отправляет сценарии из `fixtures/` на webhook n8n и сверяет ответы (`received`, `inserted`, `duplicates`, `rejected`) с ожидаемыми из `fixtures/expected_results.json`. В конце печатается "Расхождений нет." или список расхождений. Нужны пустая база и опубликованный workflow с созданным credential. Данные остаются в бд и далее `make report` строит отчёт по этим данным.

## Путь данных и распределение логики
- POST /webhook/events ->
- receive events(webhook n8n) ->
- validate events (n8n код нода) ->
- valid request (if развилка, ориентируется на фильтрацию validate events) ->:
- запрос не валиден по ветке error -> respond request error  (HTTP 422)
- запрос валиден -> insert events (n8n PostgreSQL нативная нода, вызывающая функцию записи событий insert_events) -> respond result (HTTP 200 со счётчиками)

Распределение ответственности:
- `n8n` принимает данные и проверяет их: структуру, типы, дату, перечисления. Не строит sql запрос, использует созданную PostgreSQL функцию.
- `PostgreSQL` отвечает за консистентность данных и идемпонентность. Все события из webhook попадают в функцию `insert_events`. Функция записывает новые события в таблицу `events`, а события, которые не прошли проверку, в таблицу `rejected_events`. Если событие с таким `event_id` уже есть, функция сверяет данные: если данные совпадают - это дубль, event просто попадает в счетчик дублей. Если данные другие, это конфликт, новая версия отклоняется, а старая остаётся. В конце функция возвращает счётчики и список ошибок для ответа.

## Идемпотентность и обработка ошибок
Идемпотнентность - повторная отправка того же payload не создает новых строк в таблице `events` и `rejected_events`:
- `events`: `event_id` это PRIMARY KEY, поэтому в таблицу нельзя записать два события с одним `event_id`. Если событие с таким `event_id` уже есть и данные те же, это дубль, он только считается в `duplicates`. Если данные другие, это конфликт: новая версия отклоняется с `event_id_conflict`, а старая остаётся.
- `rejected_events`: на таблице стоит уникальный индекс по паре код ошибки + хэш от содержимого события. Если то же самое отклонённое событие пришло повторно, новая строка в журнал не добавляется.
Обработка ошибок:
- Отдельное событие из батча невалидно (нет поля, неверный тип или значение, дата без пояса): оно отклоняется, остальные события батча сохраняются. Ответ 200, событие попадает в errors и в журнал rejected_events.
- Запрос целиком неверный (не JSON или нет массива events): ответ 422, ничего не записывается и в журнал не попадает, workflow составляет ответ ошибки исходя из результата `validate events` ноды.
- Сбой бд: ответ 500.
- Неполные, но допустимые данные (lead_id и author_id равны null, автор не из справочника): событие сохраняется как обычное, проблема всплывает в отчёте как data_issue.
- События читаются по occured_at, в каком порядке пришли не имеет значения и на составление отчета не влияет.

## Часовые пояса и округление временной метки
- Поле `occured_at` в бд хранится как в `Etc/UTC` часовом поясе. Рабочие часы и расчет для отчетов производитсяв часовом поясе бизнеса - `Europe/Moscow`. Конвертация происходит при расчете затраченного времени на ответ в `business_hours.py` и при составлении отчета в `csv_export.py`.
- Округление и расчет: 
    - Расчёт идёт в точной длительности с миллисекундами, статус определяется по ней до округления. Если партнер запустит обращение в `10:59:01`, первый ответ придет в `11:29:02` - обращение получит в отчете статус `answered_late` (30 минут и 1 секунда).
    - Округление до двух знаков после точки у минут делается только при составлении отчета: минуты в `report.csv` и процент соблюдения SLA в `summary.json`.
 

## Сохранность данных при перезапуске
Данные хранятся в двух Docker volume, которые описаны в `docker-compose.yml`:
- `postgres_data` - все данные PostgreSQL: таблицы `events`, `rejected_events`, `employees`, а также служебная база `n8n`, где n8n хранит свои workflow, credentials и аккаунт владельца.
- `n8n_data` - служебные файлы n8n (`/home/node/.n8n`).

Что сохраняется:
- `docker compose stop` / `docker compose start`, `docker compose down` (или `make docker-down`) и перезапуск компьютера: контейнеры удаляются или останавливаются, а volume остаются. События, журнал отклонённых событий, workflow и credentials на месте, повторно настраивать n8n не нужно.

Что теряется:
- `docker compose down -v` удаляет volume вместе со всеми данными. После этого при следующем `docker compose up` база создаётся заново: SQL-скрипты из `sql/` выполняются снова (создаётся схема, справочник сотрудников и функция `insert_events`), а n8n нужно настроить с нуля: создать владельца, credential, импортировать `n8n/workflow.json` и **ОПУБЛИКОВАТЬ** (см. раздел «Импорт workflow и credentials»).

Скрипты из `sql/` выполняются только при первом создании базы, на пустом volume. Чтобы применить их к уже работающей базе, есть `make db-apply` (повторный запуск безопасен).

Файлы отчётов в `output/` и код лежат на хосте, а не в контейнерах, поэтому от перезапуска и `down -v` не зависят.

## Проектные решения и компромиссы
**1. Запись событий делает SQL-функция `insert_events`, а не SQL внутри узла n8n.**
- n8n передаёт в неё один вызов с двумя списками (валидные и отклонённые события), а всю работу выполняет база: вставляет новые события, отличает дубль от конфликта, пишет журнал отклонённых и возвращает счётчики. Преимущества:
   - функцию можно проверить без n8n: тесты вызывают её напрямую на базе (`tests/integration/`).
   - workflow остаётся маленьким и читаемым: без циклов и веток по каждому событию или сложного sql внутри ноды.
- Компромисс: логика записи не видна на схеме workflow и не редактируется в интерфейсе n8n. Чтобы её изменить, нужно править `sql/03_insert_events.sql` и применять скрипт (`make db-apply`).

**2. Время хранится как `timestamptz`, в бизнес время переводит Python.**
- В базе лежит точный момент, поэтому `+03:00` или `Z` с одним временем считаются одним событием, а результат не зависит от пояса, в котором событие прислали или читают. Рабочие часы привязаны к Москве в одном месте кода.
- Компромисс: перевод в бизнес время нужно не забывать делать в Python при расчёте и выводе, а также форматировать при изменениях бизнес часового пояса, иначе рабочие часы сдвинутся относительно UTC. Исходный пояс события не сохраняется.

**3. `issue_code` хранит только первую найденную ошибку, а полный перечень лежит в `description`.**
 - В `issue_code` остаётся одно значение, по которому удобно фильтровать и группировать (в ТЗ он и показан как одно значение, например `invalid_occurred_at`), а для человека все проблемы события перечислены в `description`.
- Компромисс: по `issue_code` не видно, что у события несколько ошибок, чтобы это узнать, нужно читать `description`. Какая из ошибок окажется "первой", определяется порядком полей в ТЗ.
